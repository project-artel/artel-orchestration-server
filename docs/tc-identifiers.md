# 프로젝트별 TC 식별 번호 추가

TC는 프로젝트마다 `TC-001`부터 시작하는 표시 번호를 갖는다. 내부 `test_case.id`와 별도로 저장하며, 서로 다른 프로젝트는 같은 번호를 사용할 수 있다. 최소 세 자리로 표시하고 999 이후에는 자릿수를 늘린다.

## 번호 발급과 보존

- `V147_1__assign_project_test_case_numbers.sql`이 기존 TC와 소속을 확인할 수 있는 과거 검증 기록을 backfill한다. 현재 TC의 소속 프로젝트를 우선한다. 소속이 모호한 과거 기록에는 번호를 추정해서 붙이지 않는다.
- migration은 `test_case` 쓰기를 잠근 상태에서 backfill·counter·trigger 설치를 완료한다. 프로젝트별 counter와 unique constraint로 동시 생성 시 중복을 방지한다.
- 모든 생성 경로는 DB trigger를 거친다. 필터·정렬·폴더·빌드 버전·TC 내용 수정으로 번호가 바뀌지 않는다.
- TC를 삭제해도 번호 mapping을 보존한다. 발급했던 번호와 삭제된 TC의 내부 ID는 다시 사용하지 않는다. 실패한 트랜잭션이나 충돌 처리 때문에 번호 사이에 공백이 생길 수 있다.
- 번호를 발급하지 못한 모호한 과거 ID를 수동 SQL로 재사용하는 경우까지 별도로 예약하지는 않는다. 일반 생성 경로는 기존 내부 ID sequence를 사용한다.

## 조회 API 추가

프로젝트 멤버는 `GET /api/projects/{projectId}/test-case-identifiers`로 삭제된 TC를 포함한 전체 mapping을 조회한다.

```json
[{"testCaseId":"110147","caseNumber":"1"}]
```

두 값은 큰 정수의 손실을 막기 위해 문자열로 전달한다. API payload·URL·agent·SDK·CLI의 기존 내부 ID 계약은 유지한다. 화면은 `caseNumber`를 `TC-001`로 표시한다. 번호를 알 수 없으면 `TC-…`로 표시하며 내부 ID나 현재 행 순서로 번호를 만들어 내지 않는다.

## 적용과 검증

서버를 먼저 적용하고 화면을 적용한다. rollback 시에도 번호 mapping과 counter는 보존한다. 이미 작성된 이슈·실행 이름은 일괄 수정하지 않는다.

새 API·migration 테스트 11개가 프로젝트별 독립 번호, 동시 생성, 삭제 후 비재사용, 과거 기록, 권한을 검증한다. 기존 TC 내용 검토 기능을 포함한 서버 회귀 테스트 53개도 통과했다. 로컬 DB에 147.1을 적용한 뒤 프로젝트 1의 내부 ID 1과 검증용 프로젝트 110147의 내부 ID 110147이 각각 표시 번호 1을 갖는 것을 확인했다. 검증용 프로젝트에서 UI로 생성한 내부 ID 6은 표시 번호 2를 발급받았다.
