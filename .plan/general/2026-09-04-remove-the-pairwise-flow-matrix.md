# 2026-09-04 — 짝 행렬의 N제곱을 걷어낸다

- Date: 2026-09-04
- Jira: 신규 (에픽 ARTEL-770 아래)
- Status: 보류 — 실사용자가 생기면 착수한다(사용자 판단 2026-09-04).
  Step 0(정찰·골든)은 끝났고 `ScenarioFlowGoldenTest` 가 지금 답을 굳혀 두었다.

## Goal

흐름을 세우는 준비가 **케이스 수의 제곱으로 자라지 않게** 한다. 답(흐름 묶음과 순서)은
한 글자도 바뀌지 않아야 한다.

지금은 `ScenarioFlowMatrix` 가 케이스 두 개씩 모든 순서쌍에 `ScenarioPathService.findPath`
를 부른다. 실측:

| 케이스 | 칸 | 걸린 시간 |
|---:|---:|---:|
| 88 | 7,656 | 11.4초 |
| 1,000 | 999,000 | 약 25분(외삽) |

## Non-goals

- 흐름을 고르는 규칙을 바꾸지 않는다. 점수도 상한(`maxCases` 20 · `maxGaps` 6)도 그대로다.
- `state_after` 를 채우지 않는다. 그건 별개 항목이고, 이 작업은 지금 있는 값으로 한다.
- 케이스가 늘었을 때 캐시를 무효로 만드는 신호는 만들지 않는다. 지금 케이스가 느는 길은
  지도 재적재뿐이라 급하지 않다(사용자 확인).
- 저작 agent 를 부르지 않는다. 흐름은 지도와 케이스만으로 정해지므로 모델 없이 검증한다.

## 최악에서도 도는가 (착수 전에 정할 것)

**측정값을 믿고 짓지 않는다.** 아래 수치는 word-venture 한 게임의 것이고, 다른 지도를
가진 것이 없다. `바로` 가 중앙값 3번째에 나온다는 것도 이 게임의 성질일 수 있다.

그래서 네 걸음 모두 **최악이 지금과 같아야** 한다.

| 걸음 | 최악일 때 | 지금보다 나쁜가 |
|---|---|---|
| 게으른 행렬 | 흐름 계산이 모든 짝을 물어 전부 푼다 | 같다 |
| 가지치기 | `바로` 가 하나도 없어 후보를 다 본다 | 같다 |
| dispatcher 내리기 | — | 항상 낫다 |
| 흐름 캐시 | 매번 빗나가 매번 계산한다 | 같다 |

그 위에 **상한을 둔다.** 위의 넷은 상수를 줄일 뿐 차수를 안 바꾸므로, 케이스가 아주
많아지면 결국 걸린다.

- **시한.** 흐름 계산에 쓸 수 있는 시간을 정하고, 넘으면 **거기까지 만든 흐름으로 끝낸다.**
  하나도 못 만들었으면 흐름 없이 보낸다.
- **흐름 없이 보내는 것은 이미 계약에 있다.** `flows` 가 비면 모델이 예전처럼 스스로 묶고
  순서를 정한다(`ScenarioAgentRequest.flows` 의 주석). 새 실패 모양을 만드는 것이 아니라
  이미 있는 길로 물러나는 것이다.
- **몫.** 시간이 아니라 부른 횟수로도 막는다. 한 흐름을 잇는 데 쓸 `findPath` 수에 상한을
  두면 데이터가 어떻든 총량이 정해진다.

시한과 몫의 값은 착수할 때 실측으로 정한다. 지금 정하면 그것도 한 게임에 맞춘 수가 된다.

## Context / Constraints

**어디가 비싼가.** `findPath` 한 번이 `test_case` · `capability` · `scene` · `scene_edge`
를 여러 번 조회한다. 짝당 약 1.5ms 이고, 그것이 7,656번이다.

**지금 어디서 도는가.** 로그의 스레드 이름이 `reactor-tcp-nio-*` 다 — **이벤트 루프**에서
돈다. `coroutineScope` 만 쓰고 dispatcher 를 안 정해 부른 쪽 문맥을 그대로 쓴다. 지금
버티는 이유는 I/O 라 기다리며 양보하기 때문이다. **계산을 메모리로 옮기면 양보할 자리가
없어지므로, 옮기는 것과 dispatcher 를 내리는 것은 한 묶음이어야 한다.**

**답이 왜 안 바뀌는가.** 점수가 사전식이다.

    점수 = 비용×10,000 + (요구개수×100 + 진행도)
    비용: 바로 0 · 조작 1 · 거쳐서 2 · 그밖 9
    뒷부분은 1,000 을 넘지 못한다

그래서 **`바로` 하나가 나오면 다른 어떤 후보도 못 이긴다.** 그리고 `바로` 는 사이에
아무것도 안 낀다는 뜻이라, 그 후보가 설 수 있는지는 **지금 상태만 보면 안다** — 다리가
값을 바꿔 줄 일이 없다. 흐름 계산이 이미 들고 있는 `known` 으로 판단되는 자리다.

**실측 — `바로` 는 얼마나 일찍 나오나.** 케이스만으로 매긴 순서에서:

| | |
|---|---|
| 중앙값 | 3번째 |
| 평균 | 7.4 |
| 최대 | 65 |
| 끝까지 없던 출발점 | 0 / 88 |

**무엇이 후보를 열어 주는가.** 값만이 아니다.

| | 다시 볼 것 |
|---|---|
| 값이 바뀐다 | 그 값을 요구하는 케이스 — 평균 6개(변수 23개, 케이스당 전제 1.6개) |
| 화면이 바뀐다 | 그 화면의 케이스 — 7~29개(씬 7개) |
| 값을 잊는다(플레이로 지나감) | 그 값을 요구하던 케이스 |
| 전제가 아예 없는 20건 | 늘 후보 |

**메모리.** 지도 표 전체는 1.5MB 지만 실제로 들 색인은 약 136KB(케이스 88건 기준)다.
케이스 1,000건이면 1.5MB, 그런 프로젝트 135개가 힙 2GB 의 10% 다.

**흐름은 요청과 무관하다.** `(프로젝트, 케이스 묶음, 지도 판)` 에만 달렸다. 지금은 세션을
열 때마다 다시 계산한다 — 같은 프로젝트로 다섯이 열면 다섯 번 푼다.

## Approach (Checklist)

- [x] **Step 0: Recon**
  - [x] `ScenarioFlowMatrix.of` 가 모든 순서쌍을 `async` 로 푸는 것 확인
  - [x] `ScenarioFlowPlanner.of` 가 행렬을 `{ from, to -> Link }` 함수로 받는 것 확인
  - [x] `ScenarioFlowPlan` 이 걸음마다 `left` 전부에 `link()` 를 부르는 것 확인
  - [x] 행렬을 통째로 읽는 다른 소비자 확인 — `effects` 미리 읽기 · `render()` · `count()`
  - [x] 스레드 이름으로 이벤트 루프에서 도는 것 확인
  - [x] 흐름 골든 테스트로 지금 답을 굳힘 (`ScenarioFlowGoldenTest`)

- [ ] **Step 1: 게으른 행렬**
  - `ScenarioFlowMatrix` 가 `between()` 이 처음 불릴 때 풀고 기억한다. 미리 다 풀지 않는다.
  - `render()` · `count()` 는 **푼 칸만** 말한다. 기록이 줄어드는 것은 잃는 것이므로 그렇게
    적는다 — "7,656칸 중 3,657칸을 풀었다" 로.
  - `ScenarioFlowPlanner` 의 `effects` 미리 읽기가 모든 짝을 훑는다. 고른 이웃의
    `capabilityIds` 만 읽도록 뒤로 미룬다.
  - 기대: 7,656 → 약 3,657칸 (−52%). 답은 그대로.

- [ ] **Step 2: 가지치기**
  - `ScenarioFlowPlan` 이 걸음마다 후보 전부를 묻지 않는다.
    1. 케이스만으로 `요구개수×100 + 진행도` 를 매겨 오름차순으로 줄 세운다(조회 0회).
    2. 그 순서대로 `link()` 를 부른다.
    3. 지금까지 best 가 다음 후보의 하한(`base`)보다 작거나 같으면 멈춘다.
       `바로` 가 하나 나오면 곧바로 이 조건이 선다.
  - 같은 값이 여럿일 때 지금과 같은 것을 고르도록, 정렬은 `(base, 원래 자리)` 로 안정되게 한다.
  - 기대: 약 3,657 → 약 636칸 (−83%). 답은 그대로.

- [ ] **Step 3: 계산을 이벤트 루프 밖으로**
  - 행렬·흐름 계산을 `Dispatchers.Default` 로 내린다.
  - I/O 인 지금도 이벤트 루프를 10초 잡고 있으므로, 가지치기 전후와 무관하게 옳다.

- [ ] **Step 4: 흐름을 다시 쓰지 않는다**
  - `(projectId, 케이스 묶음, content_map 판)` 을 키로 흐름 묶음을 들고 있는다.
  - 무효화는 **판**으로 한다(시간이 아니라). 지도가 안 바뀌면 흐름도 안 바뀐다 —
    `CapabilityConditionReader` 가 이미 `content_map.updated_at` 으로 그렇게 한다.
  - 케이스 쪽은 **쓰는 자리에서 버린다.** 서버가 물어보지 않는다.

        케이스를 바꾸는 곳  →  그 프로젝트의 흐름을 버린다(forget)

    케이스를 바꾸는 길은 전부 우리 코드를 지난다 — 적재기(`MapTestCaseWriter`), 사용자가
    화면에서 고치는 API, 에이전트가 고치고 지우고 더하는 자리. 세 곳에서 한 줄씩이면 되고,
    도구를 따로 만들 필요도 서버가 주기적으로 물어볼 필요도 없다. `CapabilityConditionReader`
    에 넣은 `forget` 과 같은 모양이다.

  - **지문 조회는 보루로도 못 쓴다(지금은).** `select count(*), max(updated_at)` 을 재 보니
    새로 들거나 지우는 것은 잡지만 **고치는 것은 못 잡는다.**

        UPDATE 전  1 | 2026-09-02 06:44:06.873798
        UPDATE 후  1 | 2026-09-02 06:44:06.873798   ← 안 움직인다

    `MapTestCaseWriter` 가 `prior.copy(...)` 로 고쳐 쓰는데 `updatedAt` 이 옛 값 그대로
    실리고, 표에 트리거도 없다. 지문을 보루로 쓰려면 **갱신할 때 시각을 미는 일이 먼저**다.
    그 전에는 있으나 마나이므로 이 플랜에서는 쓰지 않는다.

  - 케이스마다 판을 다는 **버저닝은 넣지 않는다.** 안 바뀐 케이스까지 흔들린다.

  - 메모리를 지키려면 **개수 상한(LRU)** 을 함께 둔다. 판만 보면 프로젝트가 늘 때 안 버려진다.

    이웃 80군데(바로 55 · 거쳐서 18 · 조작 7)
  - 푼 칸 수가 7,656 → 3,657 → 636 으로 떨어진다. 이 수를 검사로 못 박는다
    (`행렬은 아직 모든 짝을 푼다` 를 걸음마다 고쳐 쓴다)
  - 짝 행렬 로그의 `ms` 가 11,400 → 1,000 안팎으로 떨어진다

## Risks & Rollback

- **Risks:**
  - 가지치기의 멈춤 조건이 틀리면 **다른 흐름이 나온다.** 골든이 그것을 잡지만, 골든은
    word-venture 한 게임이다. 다른 지도에서 어긋날 여지가 남는다.
  - `render()` 가 푼 칸만 말하게 되면 기록이 줄어든다. 지금은 막힌 자리를 무엇이 막았는지
    전부 세는데, 안 푼 칸은 셀 수 없다.
  - Step 4 의 캐시는 케이스가 늘어도 안 버려진다. 지금은 재적재뿐이라 괜찮지만, 저작 중에
    케이스를 만드는 길이 생기면 낡은 흐름을 쓴다.
  - `바로` 가 드문 지도에서는 가지치기가 거의 안 먹는다. 최악은 지금과 같다.
- **Rollback steps:**
  - Step 1·2 는 `ScenarioFlowMatrix` 를 예전처럼 미리 다 풀게 돌리면 된다. 계약이 안 바뀐다.
  - Step 4 는 캐시를 끄면 된다.
