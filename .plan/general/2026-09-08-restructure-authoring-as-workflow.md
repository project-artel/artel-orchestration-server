## Goal

저작 에이전트를 **단일 도구 루프에서 "라우터 + StateGraph 워크플로"로 재편**해,
왕복마다 전체 컨텍스트를 재전송하는 비용 구조를 원천에서 바꾼다. 판단의 자유(묶기·
순서·되묻기)는 노드 안에 유지하고, 사고를 낳던 제어 흐름의 자유(무제한 왕복)만 걷어낸다.

이 문서는 동시에 **전후 비교 기록**이다 — 현행 구조의 문제와 비용을 실측으로 박아 두고,
이행 후 같은 잣대의 실측을 빈 칸에 채워 구조 개선의 증거로 남긴다.

## Non-goals

- 오케-agent 와이어 계약 변경 (세션/WS/프레임은 동결 — 오케는 구분 못 해야 한다)
- QA 실행 쪽 변경 (저작만)
- 현행 루프의 삭제 (스트랭글러 — 기본값 갈래로 살려 두고 갈래별로 이관)
- 모델 교체 (구조만; 노드별 모델 혼합은 열어 두되 이 플랜의 목표 아님)

## Context / Constraints

### 현행 구조와, 그것이 만든 문제들 (전부 실측)

현행: `create_agent` 단일 루프. 한 턴 = 하나의 긴 대화. 케이스 전량(74k)+지도가 시스템
프롬프트에 실리고, 도구 호출(제출·조회)마다 요청이 닫혀 **전체를 재전송**한다.

### 확정된 사실 (조사·실측로 닫힌 것)

- "요청을 안 끊는 도구 호출"의 provider 중립 대안은 **없다** — 챗 API 는 stateless.
  중립 완화는 (a)싸게=캐싱 (b)작게=격리·분해 뿐. (LangChain v1 공식 문서 확인, 2026-09-08)
- LangGraph state 채널은 모델에 자동 전송되지 않는다 — 노드별 소형 프롬프트가 공식 표준형.
- 우리 파이프라인은 순서 고정 → 공식 구분상 워크플로. 권고 패턴: custom workflow
  (prompt chaining + orchestrator-worker `Send` fan-out).
- 기성품: `ModelCallLimitMiddleware`·`ToolCallLimitMiddleware`(호출 상한),
  `BedrockPromptCachingMiddleware`(수제 캐싱 클래스의 공식판).
- B 입력은 이 게임 크기에선 전건+캐시가 슬라이스보다 싸다(74k 캐시 리딩 $0.007 <
  20k 정가 $0.02). 슬라이스 전환은 케이스 수백 건부터 — push→pull 문턱과 같은 논리.

## 노드 설계 — 각 노드가 무엇을 위해 존재하는가

> 형식: 기존 → 문제 → 이 노드로 얻는 것 → **단점(숨기지 않음)**

### R. 라우터 (초소형 모델 or 규칙)

- 기존: 모든 입력(잡담·질문·저작·수정)이 전량 컨텍스트의 루프로 들어감.
- 문제: "안녕하세요"에도 74k 재읽기. 가드레일도 프롬프트 규칙에 의존.
- 얻는 것: 갈래별로 **읽을 만큼만** — 잡담/가드레일은 ~0 토큰, 질문은 조회 1번.
  라우터 자체는 수백 토큰이라 캐시 대상조차 아님(최소 1,024 미만).
- 단점: 오분류 홉 1회 추가 지연. 분류 기준 유지보수가 새로 생김. 미분류 기본값을
  현행 루프로 두어 "무동작"이 아니라 "비싸게 동작"으로 강등하는 안전망 필수.

### A. 범위 읽기 (모델·소형)

- 기존: 범위 해석이 저작 본문과 한 호출에 뭉침 — 되물음이 산문으로 새고, 해석이
  턴마다 흔들림(런 47: "튜토리얼"이 턴1 스토리, 턴2 StagePosition 0).
- 문제: 범위 오독이 저작 전체를 미달/과잉으로 만듦 ("~까지"가 맵에서 끝난 실측).
- 얻는 것: 범위 선언이 **구조로** 나옴 → 질문이 질문 채널을 탈 수 있고, B 의 입력이
  명시됨. 되물음 상한(요청당 1회)도 이 노드의 분기로 강제 가능.
- 단점: 노드가 하나 늘어 소형 호출 1회 추가. 범위 표현력(구조 스키마)이 자연어보다
  좁아질 수 있음 — 스키마 설계가 품질에 직결.

### B. 묶기·순서 (모델·요청당 1회, 전량+캐시)

- 기존: 묶기·순서가 제출 루프에 섞여 피드백을 받으며 진행 — 대신 왕복마다 전체 재읽기.
- 문제: 왕복 비용 + 어디서 틀렸는지 분리 측정 불가.
- 얻는 것: 전량 리딩이 **요청당 1회**로 국한. 출력이 구조(묶음·순서)라 걷기 잣대로
  단독 채점 가능 — 품질 계측이 판 전체에서 노드 단위로 내려옴.
- **단점(이 플랜의 유일한 진짜 미지수)**: 단발 판단 — 제출별 피드백으로 배우던 기회가
  사라짐. v9 실측(반려 0)은 루프 조건의 성적이라 단발 성적은 미측정. 반려 시 B 통재시도
  사이클이 잦으면 비용 이점이 깎임.
- 보완 옵션(하이브리드): B 를 왕복 상한 2~3의 미니 루프로 두고 **오케의 걷기 검증
  도구(check_order — dry-run 검수)**를 준다. 제출 후 반려(밖) 대신 제출 전 검증(안).
  순수 단발 vs 하이브리드는 1단계 하네스가 정한다.

### C. 문장 쓰기 (모델·묶음별 `Send` 병렬 fan-out)

- 기존: 시나리오마다 제출 호출 — 각 호출이 전체 컨텍스트 재읽기.
- 문제: 전량 판에서 호출 20~40회의 몸통. 순차라 벽시계 4~6분.
- 얻는 것: 각 worker 는 **자기 묶음(~8k)만** 받음. 병렬이라 벽시계 ~1~2분.
  실패가 묶음 단위로 국소화 — 반려 시 그 worker 만 재실행.
- 단점: 병렬 완료 순서와 저장 순서의 정렬 필요(D 에서 직렬 방출). worker 는 이웃 묶음의
  문맥을 모름 — 묶음 간 이어지는 표현("앞 시나리오에 이어")은 못 씀(B 가 제목에 담아야).

### D. 제출·검수 (코드 — LLM 0회)

- 기존: 제출이 모델의 도구 호출 — 호출 자체가 비용이고, 반려 응답도 모델이 읽어야 함.
- 문제: "제출 N번 = 전체 재읽기 N번"이라는 비용 항.
- 얻는 것: 그 비용 항의 **소멸**. 기존 reconcile(나눔·메움·검수·되찾기·저장)을 그대로
  호출 — 와이어 프레임도 동일하게 낼 수 있어 오케 무변경.
- 단점: 없음에 가깝다 — 단, 검수 반려의 수신자가 모델(즉시 반영)에서 그래프(사이클
  분기)로 바뀌므로 반려 라우팅(C 재실행이냐 B 복귀냐)을 명시 설계해야 한다.

### E. 수정 갈래 (모델·소형 + pull)

- 기존: 수정도 전량 컨텍스트 루프로 — current_scenarios 전문(실측 55.8k)이 매 턴 정가.
- 문제: 다이어트 백로그의 그 비용 + 통째 재작성 위험.
- 얻는 것: `get_scenario(전문)` + 관련 케이스 조각만 — 요약 push·전문 pull 설계가 갈래로
  자연 구현. scenario_id 교체 저장이라 멀쩡한 스텝을 안 흔듦.
- 단점: "대상 특정"이 새 실패 지점 — 못 찾으면 질문으로 빠지는 분기 필요. 큰 수정은
  본선 승격 재라우팅 필요.

### F. 질문/조회 갈래 (모델·소형 + 조회 도구 1회)

- 기존: Q&A 도 전량 프롬프트에 얹힘.
- 문제: 질문의 데이터 주인은 전부 오케(커버리지·검색·시나리오)인데 전량을 실었음.
- 얻는 것: 조회 1번 + 소형 답변. 전량 미탑재.
- 단점: 답변의 풍부함이 조회 설계에 의존 — 루프의 "전량을 보고 있는 자의 여담"은 사라짐.

### Z. 기본값 갈래 = 현행 루프 (스트랭글러 기간)

- 미분류·미이관 갈래는 현행 create_agent 로 — 빠진 갈래의 증상이 "무동작"이 아니라
  "현행처럼 (비싸게) 동작"이 되게. 이관이 끝나면 은퇴.
