## 이 문서를 읽는 다음 사람에게

저작(무엇을 묶고 어떤 순서로 놓나)은 이제 계산이 하고, **어긋난 시나리오는 안 나온다**(런 236:
7 시나리오 · 42/42 · 어긋남 0건). 그런데 실제 결과를 사람이 읽어 보니 여전히 이상했고, 원인이
저작이 아니라 **저작이 읽는 재료 — 테스트케이스 — 에 있었다.**

**저작 쪽을 더 고치기 전에 여기부터다.** 케이스가 바뀌면 저작 결과가 통째로 바뀌므로, 저작 쪽
남은 항목(문장 검사 · 막힘 무게 · 이음 비용)을 먼저 하면 두 번 재게 된다.

## Goal

저작이 읽는 케이스가 **사람과 모델 모두에게 구별되고, 전제가 그 행동의 진짜 요구조건이고,
검증할 값이 빠져 있지 않게** 한다.

## Non-goals

- 저작(시나리오 엮기) 변경. 그건 앞 문서의 일이고 여기서는 재료만 고친다.
- 관측 케이스를 **전부** 담기. 353건 중 대부분은 게임에 필요 없는 값이다 — 고르는 규칙이 이
  작업의 절반이다.
- 구버전 생성기(`specs_v2`) 되살리기. 참고는 하되 그쪽으로 돌아가지 않는다.

## 실측 (프로젝트 24 · 지도 27 · 케이스 42건 · 런 236)

### 하나. 이름이 겹친다 — 42건 중 40건

```
같은 화면 · 같은 조작 문장   13묶음 · 케이스 40건
유일한 것                    2건

Map_scene | `Return` 키를 누른다                          7건
GameClearScene | 아무 키나 누른다                          5건
EndingScene | 아무 키나 누른다 — 더 진행되지 않을 때까지     4건
StoryScene | 아무 키나 누른다 — 더 진행되지 않을 때까지     4건
StoryScene | 아무 키나 누른다                              3건
EndingScene | 아무 키나 누른다                             3건
… (나머지 7묶음 각 2건)
```

**갈리는 것은 전제뿐이고, 전제는 조작 문장에 안 드러난다.** 대가가 실측(런 236, 시나리오 802)에
나왔다 — 모델이 `1664`(저장 데이터가 **있는** 경우)에 *"저장 데이터가 없는 상태로"* 라고 썼고,
바로 아래 `1665`(진짜 없는 경우)와 **같은 문장**이 됐다. 읽는 사람은 스토리 화면을 기대하는데
다음 스텝은 지도다.

프롬프트에는 넷 줄이 다 있었다(`precondition` · `expected` · `leaves` · `to`). **몰라서가 아니라
글자로 구별이 안 돼서다.**

### 둘. 전제가 **행동의 요구조건이 아니라 코드 경로의 조건**이다

스토리 화면 7건:

```
1660  StagePosition != 5                             → Map_scene 전환
1733  waitingForAcknowledge != 0 그리고 FLAG… == 0    → Map_scene 전환      같은 기대
1661  StagePosition == 5                             → TitleScene 전환
1734  waitingForAcknowledge != 0 그리고 FLAG… == 0    → TitleScene 전환     같은 기대
1732  waitingForAcknowledge != 0 …                   → 배경 표시 변화
1735  (전제 없음)                                     → 배경 표시 변화       같은 기대
```

`waitingForAcknowledge != 0 그리고 Object.Equals(FLAG_014_END_TUTORIAL) == 0` 은 **튜토리얼
확인 대기 중**이라는 뜻이다. 적재기가 걸어간 코드 경로가 튜토리얼 컨트롤러 안이었기 때문에
붙었고, **그 경로에서는 참이지만 그 행동의 요구조건은 아니다.**

같은 기대를 말하는 짝이 전체에서 8묶음이다. 그리고 이 전제가 저작까지 그대로 흘러간다 —
흐름 계산이 `waitingForAcknowledge != 0` 을 시작 조건으로 적는 것이 그 자리다.

### 셋. 관측만 하는 것은 아예 안 담긴다

```
지도의 기능 404건
  not-a-step · observability=unknown     216건
  not-a-step · observable                137건   ← 볼 수 있는데 케이스가 없다
  runnable   · observable                 31건
  runnable   · observability=unknown      20건

케이스가 가리키는 기능                     30건
```

`v_content_map_capability` 가 `status <> 'not-a-step'` 으로 거른다. `status` 는 세
축(actionability · observability · applicability)에서 유도된 값이라 **"볼 수는 있는데 시킬 수
없는" 137건이 함께 잘린다.**

## 구버전 생성기가 이미 하던 것 (참고 자료)

**살아 있고 지금도 돌릴 수 있다** — 에이전트 저장소 `app/specs_v2`, 엔드포인트 한 줄:

```
POST localhost:8000/internal/specs/v2/test-cases     ← 근거 문서를 그대로 본문에
```

같은 문서로 낸 출력이 `scratchpad/oldgen.json` 에 있다(153건). 스토리 화면 11건이 이렇게 생겼다:

```
step: StoryScene에서 any 입력을 한다
  precondition: … (streamingCoroutine != null 그리고 IsStreaming == true)
  expected: `Canvas/ChatWindow.chatText` 의 표시 값이 `streamingText` 와 같아진다

step: StoryScene에서 any 입력을 더 진행되지 않을 때까지 반복한다
  precondition: … MapMove.StagePosition != 5
  expected: `Map_scene` 화면으로 전환된다

step: StoryScene에 진입해 관찰한다                      ← 관측형
step: `Background1 | Background2` 표시 상태를 확인한다   ← 관측형
step: StoryScene에서 `CompleteStream` 이벤트 이후 관찰한다  ← 관측형
```

**배울 것 둘:**

1. **스텝 문장이 "무엇을 하면"을 말한다.** 조작만 적는 것이 아니라 *진입해 관찰한다* ·
   *이벤트 이후 관찰한다* · *표시 상태를 확인한다* 처럼 **행위의 종류**가 문장에 있다.
2. **등급이 있다.** `ready 38 · candidate 15 · review 97 · unsupported 3`. 관측형 스텝 106건 중
   `review` 가 79건이다 — **"낼 수는 있지만 사람이 봐야 한다"를 표시할 자리**가 있었다.

주의: 구버전도 스토리의 키 입력을 **하나로 합치지는 않았다.** 셋으로 나뉘어 있고, 다만 스텝
문장이 서로 달라 구별된다. "연속 조작을 하나로"는 구버전을 베낄 것이 아니라 새로 정할 문제다.

## Approach (Checklist)

### Step 1: 케이스 이름을 "무엇을 하면 무엇이 된다"로

**규칙**: 스텝 문장은 *조작*만이 아니라 **그 케이스를 다른 형제와 가르는 조건**을 담는다.
형제란 같은 화면·같은 조작을 가진 케이스들이고, 지금 42건 중 40건이 그렇다.

```
지금
  [1660] StoryScene | 아무 키나 누른다 — 더 진행되지 않을 때까지 되풀이한다
  [1733] StoryScene | 아무 키나 누른다 — 더 진행되지 않을 때까지 되풀이한다     ← 같다
  [1664] TitleScene | `Canvas/MapSceneButton` 또는 `Canvas/continue` 을(를) 클릭한다
  [1665] TitleScene | `Canvas/MapSceneButton` 또는 `Canvas/continue` 을(를) 클릭한다  ← 같다

바꾼 뒤
  [1660] 최종 스테이지가 아닐 때 스토리를 끝까지 진행하면 지도 화면으로 넘어간다
  [1733] 튜토리얼 확인 대기 중 스토리를 끝까지 진행하면 지도 화면으로 넘어간다
  [1664] 저장 데이터가 있을 때 시작 버튼을 누르면 지도 화면으로 넘어간다
  [1665] 저장 데이터가 없을 때 시작 버튼을 누르면 스토리 화면으로 넘어간다
```

- 손댈 곳: `testcase/generator/MapTestCasePhrasing.kt`(문구) · `MapTestCaseGenerator.kt`(형제를
  아는 자리는 이미 있다 — `withInterchangeableInputs` 옆).
- **형제 사이에서만 조건을 붙인다.** 유일한 케이스에까지 붙이면 문장이 길어지기만 한다.
- 골든이 있다: `MapTestCaseGeneratorGoldenTest` · `MapTestCaseWriterGoldenTest`. **바뀌는 것이
  이 작업의 산출물이므로** 골든 차이를 눈으로 확인하고 옮긴다.
- 검증: 같은 (scene, step) 묶음이 13 → 0 이어야 한다. 위 SQL 그대로 재면 된다.

### Step 2: 전제에서 코드 경로 조건을 걷어낸다

**문제**: 같은 기대를 말하는 케이스가 8묶음이고, 한쪽 전제가 튜토리얼 컨트롤러의 조건이다.

- 먼저 **어느 것이 진짜인지 정할 규칙**을 세운다. 후보:
  - 같은 `expected_value` 를 말하는 케이스가 여럿이면 **전제가 더 적은 쪽**이 그 행동이고, 더 많은
    쪽은 그 행동이 일어나는 **한 경로**다.
  - 전제 중 그 화면의 다른 케이스 대부분에 함께 나오는 것은 배경 조건이다(`IsLocked` 가 22번).
- ⚠️ **지도만으로는 어느 쪽이 맞는지 못 가른다.** 확인은 QA 런(실제 실행)이 할 일이고 그건
  아직 한 번도 제대로 안 돌았다(끝난 시나리오 1건, 런 14). **그래서 이 단계는 "합친다"가 아니라
  "표시한다"로 시작하는 것이 안전하다** — 같은 기대를 말하는 짝을 형제로 묶어 두고, 합치는 것은
  실행이 확인한 뒤.
- 손댈 곳: `MapTestCaseGenerator.kt` 의 묶는 자리 · `ScenarioSiblingCheck`(이미 형제 개념이 있다).

### Step 3: 관측 케이스를 담되 **고른다**

**137건이 "볼 수 있는데 케이스가 없다".** 전부 담으면 안 된다 — 게임에 필요 없는 값이 너무 많다.

- 먼저 뷰를 고친다: `v_content_map_capability` 가 접힌 `status` 로 거르는 것을 **세 축으로** 바꾼다.
  지금은 "볼 수는 있는데 시킬 수 없는" 것이 통째로 잘린다.
- **고르는 규칙이 정해졌다(실측). 셋을 차례로 적용한다 — 최종 93건.**

  ```
  볼 수 있는데 케이스 없는 기능              137건
    ① 소리 · 애니메이터만 내는 것              8건  버림
    ② 조건이 `always` 이고 사전조건도 없는 것  27건  버림
    ③ 남는 104건을 (화면 · 대상 · 종류)로 접기  51개  담음

  최종   42 + 51 = 93건   (지금의 2.2배)
  ```

  담기는 51개: `active-state` 11 · `ui-value` 10 · `transform` 9 · `scene` 7 · `write` 7 ·
  `destroy` 5 · `instantiate` 1.

  **①**은 자동으로 볼 것이 아니다.

  **②가 왜 필요한지**는 슬라임 스프라이트 18건이 말해 준다 — 전부 같은 코루틴
  (`Combat.Enemies.SlimeAnimator.MoveNext()`)이고 조건이 전부 `always` 이며 사전조건이 없다.
  갈래 18개가 아니라 **배열 인덱스를 넘기는 루프 하나**다. *"그냥 늘 그렇다"* 는 검증할 것이 없고,
  QA 에이전트에게 줄 판단 근거도 없다 — 지도에 "언제 어떤 그림이어야 하는가"가 없다.

  **③은 조작 케이스와 다르게 접는 이유가 있다.**

  ```
  조작 형제   저장 있을 때 시작 / 저장 없을 때 시작   → 갈래마다 눌러 봐야 한다. 안 접는다
  관측 형제   같은 대상의 값이 조건마다 다름          → 한 번 보면 된다. 접는다
  ```

  **버리면 안 되는 것을 버릴 뻔했다.** 처음 세운 규칙("게임 로직이 조건으로 읽는 값만")은 51건만
  담고 86건을 버리는데, 그 안에 **화면 전환 9건**(게임오버·타이틀·지도·엔딩)과 대사 표시·카드
  생성·체력 표시가 들어 있었다. 코드가 조건으로 안 읽을 뿐 **QA 가 보는 것의 핵심**이다.
  *로직이 읽는 값* 이 아니라 *사람이 보는 것* 이 기준이다.

  재는 스크립트는 이 플랜 옆에 있다(`2026-08-31-observation-filter.py`).

- **접은 케이스에는 판단 근거를 함께 준다.** 남는 51개는 조건이나 사전조건이 있으므로
  *"이 조건일 때 이 값이 이렇게 된다"* 를 그대로 넘길 수 있다(`capability_effect.detail` +
  `capability_evidence.condition_tree`). 실행하는 쪽이 그것을 보고 판단한다 — QA 에이전트를
  고칠지 케이스에 노트를 실을지는 그쪽 작업과 함께 정한다.

- 케이스가 42 → 93건이 된다. 늘린 뒤 **반드시 저작을 다시 잰다** — 목록이 커질수록 모델이
  약해진다는 것이 A/B 실측이다. 다만 이제 저작은 케이스 전량 목록만 받는 것이 아니라 **계산된
  흐름**도 받으므로 예전만큼 안 흔들릴 수 있다. 그것도 재 봐야 안다.

### Step 4: 다시 저작으로

케이스가 바뀌면 저작 결과가 통째로 바뀐다. 앞 문서의 남은 항목을 **그 다음에** 잰다:

```
[ ] 문장이 구조와 어긋나는지 본다   (Step 1 이 이것을 크게 줄일 것이다 — 재고 나서 정한다)
[ ] 막힘의 무게를 잰다              "게임을 통째로 깨라"와 "키를 눌러라"가 같은 값(2)이다
[ ] 이음의 진짜 비용을 센다         화면을 나갔다 다시 들어가는 것이 한 걸음으로 세어진다
[ ] Step 5 걷어내기 (되짚기 · 나누기 · 메우기의 찾기)
```

## Validation

```
같은 (scene, step) 묶음      13묶음 40건  →  0
같은 expected 를 말하는 짝    8묶음        →  형제로 표시됨
케이스가 가리키는 기능        30 / 404     →  고른 만큼 늘어남
저작 한 판                   7 시나리오 · 42/42 · 어긋남 0건 (런 236) 과 견준다
```

한 판 돌리는 법은 앞 문서에 있다. 기록을 켜고(`ARTEL_SCENARIO_TRACE_ENABLED=true`) 양쪽 서버를
띄운 뒤 프로젝트 24 에 전건 요청을 넣으면 `.trace/run-<id>.log` 에 전 과정이 남는다.

## Risks & Rollback

- **케이스를 고치면 지금 저장된 시나리오가 전부 낡는다.** 프로젝트 24 는 실험용이라 괜찮지만,
  다시 저작해야 비교가 된다.
- **Step 2 는 지도만으로 정답을 못 낸다.** 합치기를 서두르면 진짜 갈래를 지운다. 표시부터 한다.
- Step 3 은 목록이 커져 저작 정확도를 떨어뜨릴 수 있다(실측 A/B: 목록이 커질수록 모델이 약해졌다).
  늘린 뒤 반드시 다시 잰다.
- 되돌리기: 세 단계 모두 생성기 변경이라 커밋을 나누고, 지도를 다시 적재하면 케이스가 다시 만들어진다.

## 닫힌 질문 (2026-08-31 실측으로 답이 나옴)

- **연속 조작을 하나로 합칠 것인가 → 합치지 않는다. 이미 둘 다 낸다.**

  ```
  EndingScene | 아무 키나 누른다   한 번 3건 · 연속(되풀이) 4건
  StoryScene  | 아무 키나 누른다   한 번 3건 · 연속(되풀이) 4건
  ```

  개별 조작과 연속 조작이 각각 케이스로 나온다 — 사람이 짤 때와 같은 모양이다. 문제는 알갱이가
  아니라 **이름**이었다: "한 번" 셋끼리 같은 이름이고 "연속" 넷끼리 같은 이름이다.
  **Step 1 이 이것을 없앤다.** 여기서 더 할 일은 없다.

- **관측 케이스를 고르는 규칙 → 게임이 실제로 읽는 값만.** 137 → 51. Step 3 참고.

- **`alsoReachedBy` · `calledBy` 는 저작에 안 쓴다.** 저작이 묻는 것은 "이 자리 다음에 저 자리가
  올 수 있나"와 "사이에 무엇이 필요한가" 둘뿐이고, 그 답은 씬 간선과 효과에서 나온다.
  `calledBy`(호출 그래프)는 거기 안 쓰인다. `alsoReachedBy`(같은 코드에 닿는 다른 진입점)는
  저작이 아니라 **케이스 생성**의 문제인데, 그 자리는 이미 `withoutSpecialCases` 가 접고 있다
  (실측 42 → 36). **이 플랜의 차단 요인이 아니다** — 팀 확인은 따로 남긴다.
