# 2026-08-13 — 2단계: 자연어 요청에서 TS를 제대로 뽑고, 전량을 봤다는 것을 기계로 보장하며, 남은 TC를 수치와 추천으로 되돌려준다

## Goal

1단계로 저작 Agent가 프로젝트 TestCase **전량을 알게** 됐다. 아는 것과 쓰는 것은 다르다.

2단계의 제1목표는 **저작하는 순간에 막는 것**이다. 사용자의 자연어 요청을 받고 Agent가

- 요청에 해당하는 TC를 다 보지 않은 채 시나리오를 쓰거나,
- 본 케이스를 스텝에 제대로 배치하지 않는 것

을 **기계가 검사해 거부**한다. 그리고 그 결과로 남은 TC를 **수치**와 **추천**으로 사용자에게 되돌려준다.

성공 기준은 "전량 커버"가 아니다. **"빠뜨렸는지 아무도 모르는 상태"가 사라지는 것**이 기준이다.

## Non-goals

- **TC를 골라 넣는 저작**(선택 집합이 목표/재료가 되는 두 모드) — 사용자 보류 결정(2026-08-13).
  다만 아래 1패스 구조가 그 자리를 비워 두게 설계한다(선언의 출처만 사람으로 갈아끼우면 된다).
- **TS 검증 상태(초안/검증됨/재검증필요)와 재검증 트리거** — 다음 묶음. `spec_revision`이
  올라간 케이스를 참조하는 TS를 지목할 수 있게 됐다는 사실만 기록해 둔다.
- **저장 전 린트 중 "이슈 발행 자격"** — 3단계.
- **화면 지도(`knowledge_edge`) 채우기 · TC 스키마 구조화 승격** — 별개 트랙.
- **저작이 실제 게임 상태를 이해하지 못해 QA 실행이 어긋나는 문제** — 관측됨(2026-08-13, 사용자).
  전량을 알고 다 담아도 *실행 가능한* 스텝이 나오는지는 다른 문제다. 이번 범위에서 제외하되,
  2단계 검수를 통과한 TS가 여전히 못 도는 사례가 그 트랙의 입력이 된다.
- **1회 요청으로 프로젝트 전량을 커버하는 TS 다발** — 출력 길이 한계상 불가능하다(아래 측정).

## Context / Constraints

**비용은 제약이 아니다(2026-08-13 실측).** word-venture 66건(DB 실물) + agent의 실제 렌더 형식 +
실제 저작된 스텝 30개로 단가를 재고 규모별로 환산했다. 스크립트는 `scratchpad/cost_model.py`,
결과는 [노션](https://app.notion.com/p/2026-08-13-3bb0bce5474c804191aadbf7bd3830f7)에 있다.

| 단가(실측) | 값 |
|---|---|
| TC 1건 입력(본문 포함) | 65.9 tok |
| 스텝 1건 출력 | 43.1 tok |
| system 고정부(v4) | 1,342 tok · 턴 고정부 3,334(그중 scene_scan 3,039) |

| 규모 | 요청 1회 | 전량 커버 | 전수 판정 몫 |
|---|---|---|---|
| word-venture 66 | 9.5k | **1턴** · 27.8k | 2.0% |
| 평균 300 | 26.7k | 2턴 · 158k | 3.1% |
| 최대 1000 | 78.2k | 5턴 · 430k | 9.8% |

전수 판정 출력은 **1000건에서 3,005 tok**(분리 배열 `{"in":[…],"out":[…]}`, id당 3.0). 맵 형태
`{"82":1,…}`는 5,001로 40% 비싸고 검사도 복잡하다 — 기계는 `in ∪ out == 전체`만 보면 된다.

**출력이 제약이지만 생각보다 넉넉하다.** 응답 출력 상한 16k 기준 한 턴에 **약 230건**을 쓸 수 있어,
word-venture는 1턴이면 전량이 덮이고 1000건도 5턴이다. 나누는 것은 여전히 필요하지만 병목은 아니다.
한 번의 사용자 요청이 여러 TS를 낳는 것은 정상이다(v4 프롬프트는 이미 `scenarios[]`를 허용한다).

**먼저 고칠 것이 하나 있다.** `scene_scan`(3,039 tok)이 턴 메시지(`human.md`)에 있어 매 턴 재청구된다.
세션 내내 안 바뀌는 값이라 system으로 옮기면 캐시 접두사에 들어간다 — 1000건 5턴 기준 15k로,
전수 판정보다 큰 낭비다.

**"다 봤는가"를 Agent에게 물으면 순환이다.** 다 봤냐고 물으면 다 봤다고 답한다. `spec.status`를
저작 근거로 쓰지 않기로 한 것과 같은 이유다(`spec-status-not-for-authoring`). LLM이 못 하는 것은
**빠짐없이 세는 것**이지 관련 여부를 판단하는 것이 아니다. 그러니 **세는 일을 기계가 가져온다.**

**커버리지는 이미 질의로 나온다.** `test_scenario.steps`(JSONB)의 `case_id` 합집합이 곧 커버 집합이다.
실측(2026-08-13):

| 프로젝트 | 전체 TC | 커버 | 시나리오 |
|---|---|---|---|
| 1 (E2E QA Project) | 79 | 11 | 5 |
| 3 (wordventure) | 66 | 0 | 0 |

68건이 어떤 시나리오에도 없는데 **그 숫자를 보여주는 화면이 없다.** 원장을 테이블로 만들지 않는
이유가 여기 있다 — 값이 이미 있는데 복제하면 진실이 둘이 되고, 시나리오를 고칠 때마다 동기화가 숙제로 남는다.

**저장 경로가 하나다.** Agent 결과는 자동 반영이든 수동 커밋이든 전부
`ScenarioReconcileService.reconcile`을 지난다. 검사를 여기 두면 우회 경로가 없다.
같은 클래스에 이미 "빈 배열이면 DB를 절대 건드리지 않는다"는 협상 불가 규칙이 있다 — 검사도 같은 급으로 둔다.

**마이그레이션이 필요 없을 수 있다.** 커버리지·대조·추천 모두 기존 데이터로 계산된다.
필요해지면 **V37부터**다(V36까지 사용).

**계약 변경은 양쪽 동시 배포.** 1패스 선언 필드가 Agent 결과 계약에 붙는다. 1단계와 같은 방식으로
**필드가 없으면 검사를 건너뛰는** 하위 호환을 둬서 배포 순서 의존을 없앤다.

## Approach (Checklist)

### 설계의 축 — 검토에 산출물을 만들고, 그 산출물을 기계가 센다

```
1패스   요청 → 프로젝트 TC 전 건에 대한 in/out 판정   {"in":[…], "out":[…]}
          ↓
1차 검수   in ∪ out == 프로젝트 전체 id 집합인가?
           빠진 id = 검토하지 않은 케이스 → 거부, 그 id만 다시 판정시킨다
          ↓
2패스   선언 in을 소진할 때까지 스텝을 쓴다 (TS 여러 개로 나눠도 된다 — 나누는 판단은 Agent 몫)
          ↓
2차 검수   ① in − 결과 case_id = 누락  → 저장 거부, 빠진 것만 다시 쓰게 한다
           ② 결과 − in       = 초과  → 자연어 모드는 기록만 (아래 근거)
           ③ 결과 − 프로젝트 전체 = 유령 case_id → 거부
```

**1패스를 "포함 목록"이 아니라 "전 건 판정"으로 두는 것이 이 설계의 핵심이다.** 포함된 것만 받으면
나머지를 *검토하고 뺀 것*인지 *아예 안 본 것*인지 구분할 수단이 없다 — 검사할 대상 자체가 없다.
전 건 판정을 받으면 **"검토 안 함" = "판정이 빠진 id"** 가 되어 기계가 뺄셈으로 센다. 부수 효과로
모든 id를 출력하게 강제하니 주의가 전량에 흐른다(지금은 눈에 띄는 몇 건만 보고 답해도 티가 안 난다).

**순환이 아니다.** "다 봤냐"고 묻는 것이 아니라 판정을 내놓게 하고 그 개수를 센다. 판단(무엇이
관련 있는가)은 LLM이, 계수(빠짐없이 판정·배치됐는가)는 기계가 한다.

**자연어 모드에서 초과는 거부하지 않는다.** 1패스 선언은 Agent 자신의 추정이라 절대 기준으로 삼으면
1패스에서 좁게 잡은 실수를 2패스가 고칠 길이 사라진다. 집합의 출처가 사람이 되는 선택 모드
(Non-goal, 후속)에서만 초과를 거부한다 — **초과 판정은 집합의 출처에 따라 갈린다.** 누락은 양쪽 다 막는다.

**두 검수 다 못 잡는 것: 판정이 옳았는지.** `out`으로 찍혔지만 사실 관련 있는 케이스는 어느 쪽도
못 잡는다. 1차는 "판정했다"까지, 2차는 "판정대로 했다"까지다. 프로젝트 미커버 수치가 그 뒤에 남는
유일한 그물이라, 수치를 우선순위에서 내리더라도 **빼면 안 된다.**

## Validation

- **Commands to run:**
  - orche: `./mvnw -o test -Dtest='TestScenario*,TestCase*,Scenario*' -DfailIfNoSpecifiedTests=false`
    (Maven 프로젝트다 — Gradle 아님)
  - agent: `uv run pytest tests/`
  - home: `npm run build`
- **Expected output:**
  - 자연어 요청 하나로 **여러 TS**가 나오고, 선언한 케이스가 하나도 빠지지 않는다
  - 일부러 빠뜨리게 만든 응답은 **저장되지 않고** 무엇이 빠졌는지가 사용자에게 보인다
  - 프로젝트 화면에서 미커버 수가 보이고, 저작 후 그 수가 실제로 준다
  - "뭐 테스트할까" 류의 요청에 미커버 케이스가 근거로 제안된다

## Risks & Rollback

- **Risks:**
  - **1패스가 좁게 잡으면 대조를 통과해도 실제로는 빠진다.** 대조는 "선언을 지켰는가"만 보장하고
    "선언이 옳았는가"는 보장하지 않는다. → 프로젝트 미커버 수치가 그 실패를 사후에 드러내는 안전망이다.
    둘을 함께 내는 이유가 이것이다.
  - **재시도가 길어져 턴이 느려진다.** → 재시도는 빠진 것만, 횟수 상한을 둔다. 상한에 걸리면
    저장하지 않고 사용자에게 넘긴다(조용히 절반만 저장하지 않는다).
  - **선언 집합이 커서 2패스 출력이 한계를 넘는다.** → 나누는 판단은 Agent가 하되, 한 응답에
    다 못 담으면 남은 것을 다음 턴으로 넘기는 경로가 필요하다. 설계 단계에서 정한다.
  - **커버리지 질의가 느려진다**(시나리오·스텝이 늘 때). → 실행 계획을 먼저 재고, 필요하면
    그때 인덱스를 논한다. 원장 테이블은 마지막 수단이다.

- **Rollback steps:**
  - 대조는 **선언 필드가 없으면 건너뛰도록** 만든다 → agent만 되돌리면 검사가 꺼진다.
  - 프롬프트는 `v4`를 남기고 `v5`를 신규로 추가한다 — 되돌리기가 파일 교체로 끝난다.
  - 커버리지 API·화면은 읽기 전용이라 되돌려도 데이터에 영향이 없다.
  - 스키마 변경이 없으면 마이그레이션 롤백도 없다.
