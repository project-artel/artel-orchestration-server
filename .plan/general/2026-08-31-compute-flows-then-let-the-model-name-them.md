# 2026-08-31 — 계산이 흐름을 짜고 모델이 이름을 붙인다

- Date: 2026-08-31
- Jira: None (발행 예정)
- Status: Draft

## Goal

저작이 **실행 불가능한 시나리오를 만들 수 없게** 한다. 지금은 만들 수 있고, 코드가 뒤따라가며
고치다가 다른 자리를 깬다.

실행 가능성을 정하는 두 판단 — **무엇을 한 흐름에 묶나**, **어떤 순서로 놓나** — 을 모델에서
계산으로 옮긴다. 모델은 범위를 읽고 이름을 붙이고 문장을 쓴다.

## Non-goals

- **GAP 을 줄이는 것.** "전투에서 이겨야 한다"는 지도의 천장이고 구조로 없앨 수 없다.
  줄어드는 것은 거짓 스텝이지 GAP 이 아니다.
- **실행 검증.** 아래 어긋남 검사는 게임을 돌리지 않는다. 그건 QA 런의 일이고 아직 한 번도
  제대로 안 돌았다(끝난 시나리오 1건, 런 14).
- TC 생성. 저작은 지금도 TC 를 만들지 않는다 — 지도 적재만 만든다.
- 지도 적재·SDK·QA 실행 쪽 변경.

## Context / Constraints

### 지금 구조의 결함 (전부 실측으로 확인)

1. **한 구간씩 고치고 흐름을 다시 안 본다.** 703의 19번 브리지가 20번을 살리려고 값을 0으로
   만들었고 21번을 죽였다. 그 계산은 그 자리에서 맞았다 — 21번을 안 봤을 뿐이다.
2. **묶기·순서를 모델이 42건을 들고 한다.** A/B 실측: 전량 한 번에 26시나리오/오름 9,
   여정 하나씩 9/1.
3. **되짚기가 잡고도 못 고친다.** 런 216에서 세 자리를 정확히 짚고 다시 쓰라고 시켰는데 같은
   순서를 냈다. 경로 도구가 `UNKNOWN` 일 때 "스텝을 지어내지 마라"고 지시하므로 구조적으로
   못 고친다. 35초와 모델 턴 하나가 매 판 그냥 나간다.
4. **검수가 걸어지나를 안 본다.** 담았나·지어냈나·판정했나만 본다.
5. **나누기가 지도만 보고 흐름을 안 본다.** `movableValues` 가 "지도에 그 값을 쓰는 기능이
   하나라도 있나"만 묻는다 — 방향도 값도 이 흐름이 실제로 지나가는지도 안 본다.

### 제약

- 이 설계는 **경로 서비스의 정확도에 전부를 건다.** 오늘만 세 번 틀렸다. Step 1 의 골든이
  그것을 보이게 만드는 장치이고, 그게 이 순서인 이유다.
- 특정 게임에 맞추지 않는다. word-venture 한 곳에서만 재고 있다는 것을 잊지 않는다.
- 지도는 **1회차**다. 관측 표 6개가 0행이고 씬 이동 확인 0/19 — 지금 검사는 전부 추론된 지도
  위에서 돈다. QA 런이 관측을 채우면 강해진다.

  둘 다 그렇게 갈랐다:
  - 씬 이동에 저절로 넘어가는 걸음이 끼는 길 — `TurnBattle →(이기면)→ GameClear →(누르면)→ Map`

  ```
  Step 1 전   바로 253 · 조작 196 ·             막힘 1,273
  1.5         바로 253 · 조작 350 ·             막힘 1,119
  1.6         바로 266 · 조작 463 ·             막힘   993
  1.7         바로 266 · 조작 463 · 거쳐서 992 · 막힘     1
  ```

  **남은 1칸은 `activeSelf`** — 아무 데서도 안 바뀌는 값이다. 그것만이 정말 못 가는 자리다.

- [x] **Step 2: 어긋남 검사를 검수에 넣는다** — 끝남 (ARTEL-656)

  ⚠️ **이름을 정확히 쓴다 — "걸어본다"가 아니다.** 게임을 돌리지 않는다. 지도가 적어 둔 것끼리
  부딪히는지만 본다. 할 수 있는 말은 *"이 흐름은 자기가 말한 것과 어긋난다"* 하나뿐이고,
  *"이 흐름은 실제로 된다"* 는 절대 못 한다.

  못 잡는 것을 적어 둔다: 지도가 안 적은 효과 · 관측 없는 전이 · 몇 번 눌러야 하는지 ·
  저절로 일어나는 일 · 기호 값.

  그런데도 넣는 이유는 **지금까지 잰 실행 불가가 전부 그 종류**이기 때문이다.

  초안은 `scratchpad/walk.py` 였다. **문장을 되읽지 않는 판으로 다시 짰다** — 값은 케이스의
  전제 구조와 스텝의 칸(`step_unknown_reason` · `step_source_capability_id`)에서 온다.

  **지금은 막지 않고 남긴다.** 저작이 검수에 막혀 결과가 통째로 버려지는 것이 사용자가 가장
  싫어한 일이고, 흐름 계산이 들어와 이런 자리가 애초에 안 생기게 된 뒤에 관문으로 올리는 것이
  순서다. 지금은 로그·기록·알림으로만 남는다.

  **실측에서 세 번 줄였다** — 매번 허위였고 매번 지도를 덜 읽어서였다:

  ```
  런 225   6건   브리지가 값을 바꾸는 것을 안 읽었다
  런 226   3건   `-1` 을 대입으로 읽었다(적재기가 감소와 같은 글자로 낸다)
  런 227   1건   같은 값의 세 이름을 다른 값으로 봤다
  ```

  남은 1건은 진짜다 — `LoadPlayData()` 갈래(저장 데이터 있음/없음)를 한 흐름에 담았고, 그
  값을 만드는 방법이 지도에 없다.

  그리고 이 검사가 `walk.py` 보다 **정확하다**는 것이 그 판에서 드러났다. `walk.py` 는 시나리오
  764 를 어긋났다고 짚었는데, 사이의 브리지가 타이틀을 지나며 진행도를 되돌린다 — 구조로 읽는
  쪽만 그것을 안다. 채점기는 이제 이 검사로 대체한다.

  시작 조건이 산출물이어야 하는 이유는 **좁은 범위 저작** 때문이다. 범위가 좁을수록 스텝보다
  전제가 커진다. 지금은 다 쓰고 나서 훑어 적어서 흐름 안에서 갈리는 값의 한쪽만 고른다 —
  런 217의 712 가 그렇다(`== 5` 로 시작하라는데 5번 스텝이 `!= 5`).

  케이스 집합을 받아 걸을 수 있는 흐름 묶음으로 나눈다.

  **어긋나는지 보는 규칙은 Step 2 와 같은 것을 쓴다.** 규칙이 둘이면 만드는 쪽과 보는 쪽이
  언젠가 갈라지고, 그때 어느 쪽이 맞는지 알 수 없다.

  짝 행렬 때와 같이 **보이게만 했다** — 기록에 내고 저작은 아직 안 건드린다. 모델이 낸 것과
  나란히 놓고 어느 쪽이 나은지 먼저 잰다.

  **실측(런 228 → 229):**

  ```
  228   흐름 3개 · 스텝 39/2/1        ← 이어 붙일 수 있다고 다 붙였다
  229   흐름 6개 · 스텝 12/12/8/4/5/1 · 지나갈 자리 11군데
  ```

  228 이 KDoc 에 적어 둔 그 함정이었다. 끊는 규칙(`MAX_CASES` · `MAX_GAPS`)을 넣어 229 가 됐고,
  지금 모델이 내는 것(5~9개)과 비슷한 크기다. **그 값은 제품 판단이라 부르는 쪽이 바꿀 수 있게
  열어 두었다.**

  시작 조건도 걸으면서 나오게 했다. 지도가 만들 수 있다고 말하는 값만 남긴다 — 아무 기능도
  안 쓰는 값(`IsLocked` 가 전제에 스물두 번)까지 적으면 안내가 스물여덟 줄이 된다.

  **남은 것 둘:**
  - 시작 조건에 아직 배경 조건이 섞인다(`IsLocked` · `waitingForAcknowledge`). `findWrittenValues`
    가 `active-state` 까지 세기 때문이다. 더 좁혀야 한다.
  - **흐름이 이야기가 아니다.** `1635 → 1664 → 1643 → 1654 …` 처럼 싼 순서로 뛴다. 계산은
    걸을 수 있는 것까지만 답하고 **묶고 이름 붙이는 것은 모델의 일**이다 — Step 4 다.

- [x] **Step 4: 프롬프트 v12 + 재료 교체** — 끝남 (ARTEL-658)

  모델에게 보내는 것을 케이스 전량 목록(87KB)에서 **계산된 흐름**으로 바꾼다.

  ```
  빼는 것    무엇을 묶나 · 어떤 순서로 놓나
  남기는 것  이번 요청의 범위 · 무엇을 합칠까 · 이름 · 설명 · 스텝 문장 · 대화
  ```

  프롬프트는 버전이 잠겨 있으므로 v12 를 새로 만들었다(v11 본문은 못 고친다).

  **케이스 목록은 뺀 것이 아니라 남겼다.** 문장을 쓰려면 케이스 원문이 필요하고, `flows` 가 비면
  예전 규칙으로 스스로 묶는 길이 그대로 살아 있어야 되돌리기가 된다.

  **대본이 아니라 제약으로 준다.** 순서를 바꾸거나 다른 케이스를 끼워 넣으면 걸을 수 있다는
  보장이 깨진다. 자르는 것은 안전하다 — 앞에서부터 자른 조각은 여전히 걸을 수 있다.

  **실측:**

  ```
  런 231   흐름이 프롬프트에 안 실림(API 경계에서 버려짐) → 모델이 예전처럼 묶음, 어긋남 2건
  런 232   흐름 실림 → 모델이 6개를 케이스 하나까지 그대로 따름. 어긋남 3건
  런 233   계산이 잇는 조작의 효과까지 봄 → 7 시나리오 · 42/42 · GAP 12 · 어긋남 0건
  ```

  232 가 이 단계에서 가장 중요한 실측이다. **모델은 계산을 그대로 따랐고**, 그런데도 어긋남이
  셋 나왔다 — 계산이 *"조작이 있다"* 까지만 보고 그 조작이 무엇을 바꾸는지는 안 봤기 때문이다.
  진행도를 0 으로 되돌리는 조작을 사이에 끼우고 두 칸 뒤에 5 를 요구했다. 703 과 같은 뿌리이고,
  이번에는 **어긋남 검사가 그것을 잡았다** — Step 2 를 먼저 둔 이유가 이것이다.

  기준선(런 217)과 비교:

  ```
             시나리오  전건    어긋남  GAP
  런 217         7   42/42      0     6
  런 233         7   42/42      0    12
  ```

  GAP 이 는 것은 **정상이다.** 앞서 "가는 조작이 명세에 없다"로 뭉뚱그리던 자리가 지나갈 자리로
  드러난 것이고, 줄어들 것은 거짓 스텝이지 GAP 이 아니다(Non-goals 참고).

- [x] **Step 4.5: 게임을 켜면 어디서 시작하는지를 지도에 적는다** — 끝남 (ARTEL-659)

  실제 저작 결과를 읽다가 나왔다. 시작 조건이 시나리오마다 이상하고 흐름이 게임 같지 않았는데,
  뿌리는 **계산에 "게임을 켜면 어디서 시작하나"가 없다**는 것이었다.

  씬 그래프는 순환이라 입구를 구조로는 알 수 없다(들어오는 간선이 없는 씬은 `DontDestroyOnLoad`
  하나뿐이고 그건 씬이 아니다). 그래서 계산이 *"요구가 가장 적은 케이스"* 에서 출발했다 — 계산의
  편의이지 게임의 진실이 아니다. 실측(런 233)에서 `진행도 == 5, 위치 == 0` 에서 시작하라는
  시나리오가 나왔다. 아무도 그렇게 게임을 시작하지 않는다.

  **SDK 는 안 건드린다 — 이미 보내고 있다.** `game_build.scene_scan.scenesInBuild` 가 유니티
  빌드 설정 순서 그대로이고 0번이 부팅 씬이다. 적재기가 그것을 지도에 옮겨 적고(`scene.is_entry`),
  저작은 지도에게만 묻는다는 규칙(ARTEL-466)이 그대로 산다. 마이그레이션 하나 + 적재기 몇 줄이다.

  유니티의 규약이지 명세가 그렇다고 적어 준 것이 아니므로, **"어떻게 알았는지"는 적재기 한 곳에만**
  두고 표에는 "입구"라는 사실만 남긴다.

  실측(런 234): 첫 흐름이 타이틀에서 출발하고 왕복 없이 한 방향으로 간다.

  ```
  런 233 (입구 모름)   1635 → 1664 → 1643 → …   지도에서 시작 · 타이틀 왕복
  런 234 (입구 앎)     1664 → 1635 → 1665 → 1735 → 1660 → 1643 → 1654 → …
                      타이틀 → 지도 → 타이틀 → 스토리 → 지도 → 전투 → 엔딩
  ```

  7 시나리오 · 42/42 · 어긋남 0건.

- [ ] **Step 5: 되짚기 · 나누기 · 메우기의 찾기를 걷어낸다**

  Step 4 가 검증된 뒤에만. 계산이 보장하면 셋 다 할 일이 없다.
  GAP 표시와 되묻기·사용자 답 채우기는 **그대로 남는다.**

- [ ] **Step 6: 이어 붙이는 저작**

  좁은 범위 저작은 대개 이미 있는 시나리오에 덧붙이는 일이다. 검사는 새로 쓴 부분이 아니라
  **합쳐진 결과 전체**를 봐야 한다. 지금은 앞부분과 어긋나는 덧붙임이 그대로 저장된다.

## Risks & Rollback

- **Risks:**
  - 경로 서비스가 틀리면 전부 틀린다. 오늘만 세 번 틀렸다. → Step 1 의 골든이 완화책.
  - 흐름 계산이 지금보다 잘게 쪼갤 수 있다. 지도 흐름(1636‥1641)을 한 흐름 + GAP 으로 둘지
    네 조각으로 나눌지는 **제품 판단**이라 코드가 정하지 않는다 — 계산은 둘 다 낼 수 있게 하고
    고르는 것은 모델/사용자에게 남긴다.
  - 861쌍 계산 비용이 세션 오픈을 늦출 수 있다. Step 1 에서 먼저 잰다.
  - 한 게임(word-venture)에서만 재고 있다.

- **Rollback steps:** Step 3·4·5 는 커밋을 나눠 단계별로 되돌린다. Step 1·2 는 지금 것을
  안 건드리므로 되돌릴 이유가 없다.
